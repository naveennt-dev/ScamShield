## 1. Logo: checkmark alignment

**Cause.** The logo has no SVG/PDF asset: it is drawn from vector paths in
`macos/ScamShield/Sources/ScamShieldUI/ShieldIcon.swift`, and every use comes from there (menu
popover, idle/selection screens, scanning animation, and the app icon generated by
`ScamShieldSnapshots`). The shield outline is drawn in a rect `0.82 × s` wide, but the tick's
coordinates were fractions of the full `s × s` square. Its centre therefore sat at `0.505 s`
instead of the shield's `0.41 s`: **11.6 % of the shield's width to the right**, and 1.7 % low.

**Fix (in the source, once).**
- `ShieldShape.visualCenter = (0.500, 0.488)` is the area centroid of the shield path. The shield
  narrows to a point, so its visual centre sits slightly above the frame's middle.
- The new `ShieldCheckShape` draws the tick in the **same rect as the shield**, with its bounding
  box centred on `visualCenter`. Its size (0.35 × 0.25 of the logo height), stroke widths, caps,
  colours and the shield itself are unchanged.
- The menu-bar template icon's "lens" dot was also about 1 pt low at 18 pt. It is now centred on
  `visualCenter` too.

**Verification (actually done).**
- Unit tests (`Tests/ScamShieldUITests`) rasterise the real paths. They check that
  `visualCenter` matches the measured centroid within 0.3 %, that the stroked tick is centred
  within 0.5 % at three stroke widths, and that the tick's size is unchanged.
- Rendered pixels were measured at each real size. The horizontal offset is 0.00 pt everywhere.
  The vertical residual is up to 0.37 pt (largest on the 1× menu-bar icon), which is below one
  pixel.

  | Rendering | Horizontal | Vertical |
  |---|---|---|
  | App icon, 1024 px | 0.0 % | +0.2 % |
  | Popover mark (22 × 26 pt, @2x) | 0.0 % | +0.5 % |
  | Scanning mark (58 × 70 pt, @2x) | 0.0 % | +0.5 % |
  | Idle mark (70 × 84 pt, @2x) | 0.0 % | +0.3 % |
  | Menu-bar icon, 18 pt @2x | 0.0 % | −0.2 % |
  | Menu-bar icon, 18 pt @1x | 0.0 % | +2.3 % (0.37 pt) |

- I also inspected zoomed renders of all of these by eye; the tick reads as centred.
- The snapshot tool now also writes `menubar-icon@1x.png`, `menubar-icon@2x.png` and
  `logo-sizes@2x.png` for future review.
- **Not checked by eye:** the live icon in your actual menu bar. Only offscreen renders of the
  same image were inspected.

## 2. Draggable scanner window

> **Correction (2026-10-10, later the same day).** The drag implementation described in this
> section **did not work with a real mouse**. The user reported that the card still could not be
> moved.
>
> - **Original approach:** `NSWindow.performDrag(with:)` (a window-server drag) on a transparent
>   handle. The automated checks only verified *hit-testing* (which view would receive a click)
>   and a programmatic `setFrameOrigin`; neither delivers a mouse event, so they could not detect
>   that `performDrag` doesn't move this non-activating panel of a menu-bar-only app. The earlier
>   "hand-held drag: reported done by the user" entry is withdrawn.
> - **Replacement:** explicit mouse tracking (mouse-down / dragged / up moving the real window).
> - **Evidence it now works:** a self-test that sends real AppKit mouse events through
>   `NSWindow.sendEvent`, and a physical drag recorded in the app's log.
>
> Details: `phase-4-completion.md` §A.

**Presentation.** There are two windows:
- **Menu popover.** The menu-bar click opens a transient `NSPopover` anchored to the icon. It's a
  menu: it closes when you click elsewhere, so it never stays in the way, and it remains anchored
  by design.
- **Scanner card.** This is the window that showed the scan and the result. It was already a
  dedicated borderless `NSPanel`, so no `MenuBarExtra` migration was needed. It was the window
  that "got in the way" for four reasons:
  - it sat at `.statusBar` level, above menus and every app;
  - it followed you to every Space;
  - it re-centred every time it reappeared;
  - it could not be dragged: `isMovableByWindowBackground` doesn't work through SwiftUI's
    hosting view.

**Changes** (`ScannerPanelController.swift`, `WindowDragArea.swift`, `ScannerView.swift`):

| | Before | After |
|---|---|---|
| Drag | none in practice | 44 pt header strip along the top, plus the logo and title on the idle, scanning and selection screens. ~~Uses `NSWindow.performDrag`~~ (didn't move the panel; replaced in Phase 4 by explicit mouse tracking — see the correction above). The open-hand cursor marks the handle. |
| Buttons | — | ✕ sits above the strip in z-order and is never a drag handle. Result buttons are outside the strip. Background dragging is off, so a button press never turns into a drag. |
| Window level | `.statusBar` (above everything) | `.floating`: ordinary utility-panel level. Below menus, Spotlight and alerts. |
| Spaces | followed you to every Space | opens on the Space you are on (`moveToActiveSpace`) |
| Position | re-centred on every show | see *Position persistence* below |
| SwiftUI updates | hosting view could resize the window | `sizingOptions = []`. The fixed-size card can't be resized or moved by state changes. |
| Focus | — | Dragging never makes the card key (`becomesKeyOnlyIfNeeded` + `needsPanelToBecomeKey = false`). The Phase 3 fix stays in place: the card only takes focus for results, so Esc / ✕ / Quit behave as before. |
| Instances | single lazy panel | unchanged, and now tested: menu actions and the hotkey reuse the one window |

**Position persistence**
- **Before any drag:** the card opens centred on the screen under the pointer, as before.
- **After you drag it:** it stays exactly there for the rest of the app session. That holds
  through every scan stage, OCR, results, close/reopen, and region selection (where the card
  hides while you select, then comes back to your spot).
- **Session only:** quitting the app forgets the position, as specified.
- **Display changes:** if the card's header would no longer be fully on any screen (display
  unplugged, arrangement changed, resolution changed), it is moved onto the screen it overlaps
  most, or the main screen. Otherwise your placement is left alone. This geometry is in
  `ScamShieldCore/Scanner/PanelPlacement.swift`, covered by unit tests.

**Verification**
- **Automated (in the running app's self-test):**
  - the header hit-tests to the drag handle, and ✕ does not;
  - a drag never takes focus;
  - the window level is floating and not shown on every Space;
  - a user move is remembered;
  - the origin is identical at every phase of a scan and after close/reopen;
  - the card returns to the same spot after a region selection;
  - there is a single scanner window after repeated menu and hotkey scans;
  - a card left on a missing display comes back on screen.
- **Not automated:** a physical mouse drag. macOS only allows synthetic mouse drags from a process
  with Accessibility permission, and neither the terminal nor the app has it. The self-test moves
  the window through the same code path a drag triggers (`windowDidMove`), but a hand-held drag
  remains a manual check (below).

## 3. Self-test: why the final Phase 3 run failed

The final run in the Phase 3 report was **32 / 35**, not 33 / 35 as reported then. That miscount
is corrected here. There were three failures:

| Check | Cause | Evidence | Fix |
|---|---|---|---|
| `local API analysed the OCR text` | **Real mouse click** on the card's ✕ while the test was waiting for the result | close reason `close button [type=2 (leftMouseUp) at=(944,850)]`; the self-test sends no mouse events, and (944,850) is exactly where ✕ was. The earlier 11:08 run shows the same click on four previews in a row. | During the self-test the card ignores mouse input (clicks pass through to whatever is behind it). The test closes it programmatically. |
| `menu popover opens` | Not attributable: no diagnostics were recorded. Most likely the same outside activity, since a transient popover closes on any click elsewhere. | It passed in every other run, including the three runs since. | The check now waits for the popover's `didShow` event, polling up to 3 s instead of one fixed 600 ms sleep, and records why it closed and whether the app was active. |
| `quit via NSApp.terminate` | **Test-harness bug:** when any in-app check failed, the self-test exited with `exit(1)` and never ran the Quit path, so this check failed automatically | `finish()` called `exit(1)` before `NSApp.terminate` | The self-test always leaves through the real Quit path; pass/fail comes from the report. |

The self-test also records any real keyboard or mouse input that reaches ScamShield's windows,
and prints it (`INFO real user input … : N`) so future failures can be attributed. No checks were
removed or relaxed. Nine window checks were added.

A test-sequencing bug in one of the new checks was found and fixed along the way. An async menu
action re-opened the card after the test had closed it.
